# relational-paths 0.3.0 — от метаданных к отчёту

[README](../../README.md) · [Versions](../index.md) · [English](integration.en.md) · [Русский](integration.ru.md) · [API](reference.ru.md)

## Что вы описываете

Schema — разрешённая карта бизнес-связей, по которым могут строиться отчёты. Роль обозначает одно вхождение таблицы: платёжный адрес и доставка могут использовать одну физическую таблицу через разные роли. Связь — направленный набор равенств, включая все части составного ключа. Правило отчёта становится явным и переиспользуемым.

Используйте библиотеку, если поля отчёта меняются или несколько сервисов повторяют правила соединений. Для одного фиксированного запроса обычный SQL с параметрами часто проще. Библиотека не выводит права доступа, физические внешние ключи и кардинальность строк.

## 1. Подключить к существующему приложению

Возьмите Maven- или Gradle-зависимость из README. Core не требует runtime-зависимостей и настройки Spring. База байткода — Java 17; 21/25 и optional 27 сохраняют тот же API без preview. Готовность исходников не означает доступность пакета: публикация в Maven Central ожидается.

```text
src/main/java/example/OrderReport.java
```

Полный [OrderReport.java](examples/OrderReport.java) можно перенести в пакет сервиса. Метод main — только конечная проверка; конструктор и query предназначены для приложения.

## 2. Один раз объявить метаданные

```java
var schema = Schema.builder()
    .table("orders", "sales.orders", "id", "customer_id", "tenant_id")
    .table("customer", "sales.customer", "id", "name", "tenant_id")
    .relationship("customer", "orders", "customer",
        new ColumnPair("customer_id", "id"), new ColumnPair("tenant_id", "tenant_id"))
    .build();
var queries = new RelationalQueries(schema);
```

table принимает логическую роль, физическую table/schema.table и разрешённые колонки. relationship использует стоимость 1; overload с положительным int перед ColumnPair задаёт смысловое предпочтение. Schema.builder изменяем и используется при запуске; build создаёт снимок. Существующие конструкторы сохранены.

Равенство арендатора в примере — намеренное правило приложения. Без него одинаковые ID клиентов разных арендаторов могут соединиться. Объявление колонки — разрешение в метаданных, а не доказательство права конкретного пользователя.

## 3. Переиспользовать шаблон и добавить параметры запроса

```java
var template = queries.from("orders").select("orders.id", "customer.name");
var query = template.whereEqual("orders.tenant_id", 42L)
    .whereEqual("customer.name", "Alice").build();
```

Select неизменяем. Каждый select/where/via возвращает новый объект: сохраняйте результат. Роли выбранных полей и фильтров автоматически становятся целями планировщика. Исходный шаблон можно разделять между запросами: фильтры другого арендатора не накапливаются.

Строка колонки содержит ровно одну точку: logicalRole.column. Физическое schema.table используется только в метаданных. Выражения, направление сортировки и дополнительные точки отклоняются. where поддерживает EQ/NE/LT/LE/GT/GE; EQ/NE с null дают IS NULL/IS NOT NULL без параметра.

## 4. Проверить, связать параметры и выполнить

```java
query.explain();
query.sql();
query.bindings();
```

Пример создаёт маршрут customer и параметры [42, "Alice"]. JDBC получает SQL и упорядоченные значения отдельно. Выходные алиасы c0, c1 следуют порядку проекции. Полный сервис/контроллер JdbcTemplate находится в примере Spring; core также работает с PreparedStatement приложения.

Планирование синхронно и выполняется в памяти без фоновых ресурсов. У планировщика нечего закрывать или отменять; отмена SQL, тайм-аут statement, пул и согласованность транзакций относятся к слою выполнения.

## 5. Разрешить бизнес-альтернативы

Два пути равной стоимости вызывают AmbiguousPathException с двумя примерами маршрутов. Не выбирайте первый вариант в служебном коде: выберите бизнес-связь. Для схемы адресов используйте via("address", "shipping"). Цель должна встречаться в проекции или фильтрах; повторный via той же цели отклоняется. Более длинный явный маршрут допустим, но проверяется.

Для одновременного платёжного адреса и доставки опишите две роли одной таблицы. Планы нескольких целей разделяют общие начала путей, отклоняют конфликтующие входящие пути и не минимизируют общую стоимость дерева. Положительный вес задаёт бизнес-предпочтение, а не задержку БД.

## 6. Лимиты, ошибки и проверка

SearchLimits.DEFAULT ограничивает 512 ролей, 8192 связи и 8192 посещения рёбер за автоматический поиск. Даже небольшая цель может потребовать обхода всех достижимых рёбер. Лимит приводит к ошибке, а не усечению результата. new RelationalQueries(new JoinPlanner(schema, customLimits)) сохраняет ограничения приложения.

| Симптом | Действие |
|---|---|
| AmbiguousPathException | Выберите via либо разделите роли таблицы; изучите candidates. |
| PlanningException | Проверьте направление, связность, явные маршруты и лимиты. |
| IllegalArgumentException | Проверьте объявленные колонки, синтаксис role.column и непустую проекцию. |
| Неожиданные дубли/пропуски строк | Проверьте кардинальность INNER JOIN и данные: планировщик не удаляет дубли. |

Скачиваемый сервис скомпилирован и запущен с установленным JAR. Новые проверки покрывают цели из фильтров, неизменяемые шаблоны, неоднозначность/маршруты, лимиты, строки инъекции, null и снимки метаданных. Команды проверки и ограничения публикации находятся в CONTRIBUTING.

## Что нужно знать

Метаданные — бизнес-правила; фасад убирает повторную обвязку, но не решения приложения. Закрепляйте проекцию/маршруты в сервисах, связывайте непроверенные значения, проверяйте права до построения запроса и ограничивайте выполнение на уровне БД.
